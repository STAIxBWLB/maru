<objective>
Make the two ship-isolation promises verifiable by a machine, and put `e2e-native/` under
the same typecheck and lint gates as every other tree in the repository.

Purpose: D-10 says declaring the intent and checking the output are different acts, and
only the second one catches a stray build flag or a feature that arrived through a
dependency. Plan 06-01 made the declaration - a default-off cargo feature - and plan 06-02
made the frontend half build-gated. This plan writes the independent check over what the
build actually produced and wires it into `make verify`. D-15's tsconfig and ESLint
registration lands here too, because both are about the same thing: runner code that no
gate looks at is runner code that stops compiling six weeks from now.

Output: `tsconfig.e2e-native.json` registered in the root project references and the ESLint
files list, and `scripts/check-native-e2e-isolation.mjs` chained into the frontend build.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build inputs -> shipped artifact | A Vite flag or a cargo feature intended for the runner can reach a build a user installs |
| Source declaration -> produced artifact | A correct declaration can still produce a wrong artifact via a stray flag or a feature arriving through a dependency |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Information Disclosure | Shipped frontend bundle | high | mitigate | The guard reads `dist/assets/*.js` for the bridge namespace; chained into `build:frontend` so `make verify` carries it on every run, and proven fail-first by building with the runner flag on |
| T-06-01b | Information Disclosure / Elevation of Privilege | Shipped binary carrying a listening embedded WebDriver server | high | mitigate | The guard's `--binary` mode scans the produced, unstripped debug no-bundle binary for the plugin crate's own name, wired into `release-checks` between the Tauri build and the artifact prune, so `release-preflight` inherits it. This is the check that catches a stray build flag or a feature arriving through another crate's dependency table, which the manifest assertions structurally cannot see |
| T-06-09 | Tampering | The guard itself | medium | mitigate | Both red cases are produced by real builds - the frontend flag on, the cargo feature on - never by patching a source file, so a guard searching for the wrong string shows up immediately as a false pass in the drill rather than as a permanent silent green |
| T-06-10 | Denial of Service | `cargo metadata` inside the frontend build chain | low | accept | `--no-deps --offline` reads workspace manifests only, takes no build lock and touches no registry. Kept as a cheap early-warning check alongside the binary scan, not as a substitute for it |
| T-06-13 | Information Disclosure | A stripped release binary | low | accept | The binary scan targets the unstripped debug no-bundle build, resolved with the same default feature set the release uses.
