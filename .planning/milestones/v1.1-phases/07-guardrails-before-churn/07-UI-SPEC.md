## Interaction Contract (PERF-06 — the phase's only UI surface)

### 1. Switcher composition after removal

The documents view switcher (Sidebar `type-filters` region, `Sidebar.tsx:225-251`) renders, in order:

1. **All** row (leading type-dot, total `contentCount`) — unchanged.
2. **Drafts** row (`FileText` icon, count) — unchanged.
3. **Archive** row (`Archive` icon, count) — unchanged.
4. **Recently Updated** row (`Clock` icon, count) — unchanged.
5. **Custom views** — unchanged.

The **Inbox** row (`Inbox` icon + count) is removed from `builtInViews` (`Sidebar.tsx:88-97`). No row, icon, label, or count remains in the documents switcher. This is the entire visual delta.

### 2. Behavior when persisted state references the removed view

Persisted workspace state (`documentFilterByVisibility` in `workspaceStore.ts`, per-visibility `private`/`public`) can hold `{ kind: "view", view: "inbox" }` from before the upgrade (RESEARCH Open Question 3). Contract:

- **Fail-open reset, no error UI.** On load, any persisted filter of shape `{ kind: "view", view: "inbox" }` (or any built-in view value not in the post-removal union) is reset to `{ kind: "all" }` — the same idiom and code position as the existing `pruneCustomDocumentFiltersInState` (`workspaceStore.ts:212-232`). Mirror that function's shape (e.g. extend the prune to built-in views against a valid-set parameter, or add a sibling prune called from the same MainApp effect).
- **No banner, no toast, no first-run notice.** The user lands on the All view with the full document list; the migration is silent. This matches D-01's principle extended across the phase: removals and recoveries are normal operation, not events the user acts on.
- **All-view content after reset:** the document index no longer contains `inbox/...` rows (backend exclusion), so the All view count drops by the removed rows — the user-visible count change documented in REQUIREMENTS.md (11,488 → ~9,582 on the reference workspace). No copy explains this; it is the intended behavior.

### 3. Count badges

`builtInDocumentViewCounts` in `App.tsx:1302-1309` loses the `inbox` entry along with the `BuiltInDocumentView` union member (`documentIndex.ts:5`) and the `case "inbox"` in `matchesBuiltInView` (`documentIndex.ts:273-274`). The remaining three built-in counts behave exactly as today. The standalone Inbox **pane** (app mode) and its pending-item queue are untouched — the badge/queue work there is a different surface and stays.

### 4. Surfaces that must NOT change (regression watch)

These are user-visible and unchanged; they are the contract's "no user-visible regression" half:

- **Inbox pane**: still lists pending items and drop/auto arrivals; empty state, row layout, and actions unchanged.
- **Files browser**: still resolves and opens `inbox/` paths.
- **Content search**: still resolves `inbox/` paths.
- **Drafts / Archive / Recently Updated views**: filtering and counts unchanged.
- **No dead UI**: no disabled/grayed Inbox row, no "removed" placeholder, no settings toggle resurrecting it.

### 5. i18n cleanup

Remove the `sidebar.view.inbox` key from both `src/lib/i18n/locales/en.ts:601` and `src/lib/i18n/locales/ko.ts:554` (parity is enforced by `lint-i18n`; both must go together). The `Inbox` icon import in `Sidebar.tsx` goes with the row. `lint-i18n` checks key parity and hardcoded strings, not key usage — but the key is dead after removal and must not be left as drift. No new keys are added.

### 6. Copy/empty-state implications

- No new empty states are introduced; the removed view had no dedicated empty state (it rendered the shared empty document-list region, which the remaining views still use).
- No new copy of any kind. The phase's entire user-facing textual surface is the absence of one switcher label.
- Existing Playwright inbox spec (`e2e/inbox*.spec.ts`) and unit tests referencing the inbox view shape (`outlinePaneStore.test.ts:168,176`, `documentIndex.test.ts:111`) are updated as part of the removal, per RESEARCH Open Question 3.
