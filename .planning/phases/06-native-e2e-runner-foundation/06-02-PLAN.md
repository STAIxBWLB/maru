<objective>
Give the native runner the two independent ways of seeing a real PTY that D-05 requires:
an exact text mirror of the terminal screen grid, and a pixel readback proving the canvas
region was painted. Then spend both of them on one flow that runs a real command in a real
shell.

Purpose: the terminal renders to `<canvas aria-hidden="true">`, so DOM queries see nothing
at all. ROADMAP criterion 2 asks for the canvas assertion; D-05 adds the text mirror
because the ink check alone cannot say *what* the terminal printed, and Phase 9's SIGHUP
work needs to check a named string. Implements D-05, D-06 and D-13 surface 2.

Output: `src/lib/nativeE2eBridge.ts` with its registration entry points, the registration
site in `NativeTerminalView.tsx`, `e2e-native/helpers/ptyAssertions.ts`, and
`e2e-native/specs/pty.spec.ts`.
</objective>

    Write `e2e-native/helpers/ptyAssertions.ts` exporting the pair D-05 requires, plus the
    two tuning constants so the threshold is a named value rather than a magic number.

    `readTerminalText(sessionId)` runs a `browser.execute` that reads
    `window.__MARU_NATIVE_E2E__?.terminalText(sessionId) ?? null` and returns it. If the
    namespace is missing, throw with a message pointing at
    `pnpm build:frontend:native-e2e` - a missing bridge means the wrong frontend build is
    in `dist/`, and that is the mistake worth naming explicitly rather than reporting as
    "expected string, got null".

    `assertTerminalInk(canvasSelector, options)` runs a `browser.execute` that takes the 2D
    context of the matched canvas and calls `getImageData` over a sample rectangle. Use the
    full canvas width and the top 25% of its height in device pixels, read from
    `canvas.width` / `canvas.height` rather than from CSS geometry, so the sample follows
    `devicePixelRatio` instead of fighting it. Determine the background empirically: take
    the most frequent RGBA quadruple in the sampled region as the background, then count
    the pixels differing from it by more than `INK_CHANNEL_TOLERANCE` in any channel. Do
    not read the palette or the theme - deriving the background from the sample is what
    makes the check independent of `data-terminal-theme`, of the runner's colour profile,
    and of the font. Fail unless the differing-pixel ratio is at least `INK_MIN_RATIO`.

    Set `INK_CHANNEL_TOLERANCE` to 8 and `INK_MIN_RATIO` to 0.002, with a one-line comment
    on each saying what it defends against: the tolerance absorbs subpixel antialiasing on
    a Retina runner, and the ratio is low enough that a single short line of text clears it
    while an entirely unpainted or uniformly filled canvas returns zero.

    The canvas is painted by `fillText` and `fillRect` calls, never by `drawImage` from an
    external source, so `getImageData` is not subject to cross-origin tainting whatever
    origin Tauri's custom protocol serves the page from. If a `SecurityError` ever appears
    here it is a real regression in how the terminal paints, not a test problem - let it
    propagate rather than catching it.

    Write `e2e-native/specs/pty.spec.ts` as one flow. Open the tool panel by clicking
    `.terminal-title`, start a shell from the first enabled button in `.terminal-launchers`,
    wait for `.native-terminal-view[data-session-id]` to exist and read its
    `data-session-id`, focus `.native-terminal-input`, and send a command whose *output*
    carries a marker the typed line does not. Type a shell expression that produces the
    marker only after the shell evaluates it - for example an `echo` whose argument is
    split by an empty quoted pair, so the typed characters and the printed line differ.
    Then poll `readTerminalText(sessionId)` until it contains the printed marker, and
    finally call `assertTerminalInk` on
    `.native-terminal-view[data-session-id="<id>"] .native-terminal-canvas`.

    The marker split is the point of the whole spec: if the assertion matched the typed
    characters, a terminal that echoed input and never spawned a child would pass. Put that
    reasoning in a comment above the command so a later author does not "simplify" it back
    to a plain echo.

    Keep it to this one flow. D-14 reserves suite breadth for the phases that need it;
