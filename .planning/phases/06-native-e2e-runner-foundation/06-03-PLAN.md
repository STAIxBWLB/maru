<objective>
Settle, on evidence rather than assumption, what a synthetic event stream can and cannot do
to the two surfaces that handle IME composition themselves, and give D-13's fourth surface
the one living test it can honestly have.

Purpose: ROADMAP criterion 4 asks whether synthetic key events substitute for real OS-level
IME input. D-07 makes that a two-surface question because the terminal carries hand-written
composition handling including a trailing-duplicate guard, while the rich editor is a
ProseMirror-family surface that handles composition its own way, and a single surface could
return a verdict that does not generalise. D-08 then splits the outcome in two: a native
regression test for whatever synthetic events do reach, and a named human checklist for
whatever they do not. The macOS menu bar is outside the webview entirely and the
Accessibility permission wall keeps it unscriptable, so the automatable half is the command
path the menu emits into.

Output: `e2e-native/specs/ime.spec.ts`, `e2e-native/specs/menu.spec.ts`, the menu-command
dispatcher registration in `src/App.tsx`, and both verdicts appended to
`docs/native-e2e.md`.

This plan does not presuppose either verdict. Both branches leave the same artifacts behind;
only what the document records differs.
</objective>

    Test both mechanisms per surface, in this order. First, WebDriver key input: send the

    surface; a mechanism that changes no state is a negative result to record, not a
    failure to retry around.

    The trailing-duplicate guard is the specific thing worth exercising here -
    `isTrailingCompositionDuplicate` drops a repeated syllable only inside a 100 ms window

    it by opening a seeded markdown document and switching to the rich editing mode the app

    observable is the document text in the editor after `compositionend`.
