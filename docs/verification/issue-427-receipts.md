# Runtime and persistence contract

- All installed jobs now use the existing `jobs exec` CLI wrapper; Repeat keeps its existing interval/calendar cadence and does not acquire daily-fire dedup. Reinstall existing direct Repeat plists to activate receipts. Run now rejects legacy, malformed, drifted, or differently bound installed plists before queueing a nonce or kickstarting. Canonical generated wrapper arguments must identify either the current Maru executable or the executable path and SHA-256 recorded by the new installer before bootstrap. Canonical aliases of those executable paths are accepted. After installation, distinct desktop/CLI callers retain Run now interoperability without invoking an unknown executable as a probe. Older cross-launcher wrappers without provenance require one reinstall. Local provenance assumes untampered filesystem state and is not a signed binary attestation. This prevents old direct providers from leaving a nonce that a later wrapper would replay. Manual requests keep distinct IDs, and missedFire guards cannot consume them.
- History lives at `.maru/jobs-state/<job-id>.receipts.json`, latest 100 receipts, exposed as `JobStatus.receipts` through the existing `jobs_list` command. No additional IPC command is registered. IPC readback reads a bounded atomic snapshot without mutating files; process reconciliation is displayed there and durably applied by the execution path.
- Main launchd invocations use the `calendar` source, encompassing interval and run-at-load events: launchd does not expose the exact event reason to its child. The guard path is `recovery`; explicit queued requests are `manual`. Calendar event kind is not claimed as separately observed.
- The receipt freezes the manifest revision hash, source, logical daily fire, request/run IDs, native launcher and child creation identities, admission/start/finish times, process outcome and independent verification state. No job verifier is currently configured, so verification is `notRequested` even for exit 0.
- macOS native creation identities use `PROC_PIDTBSDINFO` seconds/microseconds; Linux uses boot ID and `/proc` creation ticks. An ownerless mission record is not process evidence.
- Admission precedes spawning. One local timestamp freezes the logical run envelope start and daily-fire attribution before durable admission publication; observed child start remains a separate timestamp. Normal completion and exit-before-ledger crash reconciliation use the same receipt-to-ledger helper, so an admission crossing the next fire cannot alter attribution or suppress that next fire. A launcher crash with no persisted child identity leaves the spawn window uncertain; the receipt becomes interrupted and remains nonterminal to prevent automatic provider replay. A live orphan child also prevents another run. Native child death or PID reuse closes a receipt as interrupted, without retrying or signaling that child. Automatic invocations will not replay an interrupted receipt for the same logical daily fire; an explicit manual request can resume only once native ownership is cleared.
- An exit receipt persisted before a crash is replayed only into the success-fire ledger. It never launches a provider. The receipt remains independently readable if final ledger persistence fails.
- Completed rows can be evicted at the history bound; uncertain live rows cannot. Exhausting the bound with uncertain rows fails admission.
